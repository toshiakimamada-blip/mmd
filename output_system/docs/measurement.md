# 性能の測定（処理ログと集計コマンド）

字幕の遅れ・会議開始時の待ち時間・メモリの使用量を、アプリが処理ログへ記録し、集計コマンドで表にするための文書です。設計の根拠は、基本設計書の横断設計規約「ログの種別と項目」、非機能要件設計書「目標ごとの手立てと測り方」「字幕の遅れの判定から除く区間」「実際に使う状態での測定」、ADR の「未決定・要確認」1・14 にあります。

利用者が自分の PC で測る手順は、[measure-early.md](measure-early.md) にあります。

## 処理ログの項目

どの行にも `timestamp`（UTC・ミリ秒）、`log_type`（`processing`）、`level` が付きます。項目は、`backend/src/meeting_interpreter/logs/fields.py` の許可リストにあるものだけを出します。本文・タイトル・要約・質問は出ません。出す値は、日時・数・短い英数字の語だけです。

### 字幕を画面へ送った時点（`subtitle_sent`）

保存が確定し、通知を送った直後に、字幕 1 件につき 1 行を出します。保存に失敗した字幕は画面へ送らないため、この行も出ません（エラーログが出ます）。翻訳に失敗した字幕と、中断する会議の字幕も出ます。

| 項目 | 意味 |
|---|---|
| `trace_id` | 処理の識別子（発話の区切り 1 つに 1 つ） |
| `meeting_id` | 会議番号 |
| `received_at` | 先頭の音声がアプリサーバーへ届いた日時 |
| `sent_at` | 字幕を画面へ送った日時。字幕が区間の内か外かは、この日時で決める |
| `duration_ms` | 字幕の遅れ（ミリ秒）。`sent_at` − `received_at` |
| `audio_ms` | 発話の区切りの音声の長さ。字幕の遅れの配分の「発話の区切りができるまで」にあたる |
| `wait_ms` | 待ち。発話の区切りができてから、通訳ワーカーが処理を始めるまで |
| `transcribe_ms` | 文字起こしの所要時間 |
| `translate_ms` | 翻訳の所要時間。翻訳に失敗した字幕は、失敗までの時間 |
| `save_notify_ms` | 保存と通知の所要時間 |
| `original_char_count` | 英語の原文の文字数 |
| `translated_char_count` | 日本語訳の文字数。翻訳に失敗した字幕は 0 |
| `first_subtitle_ms` | 会議の最初の字幕の行だけに付く。会議を作った時点から、最初の字幕を画面へ送るまでの時間 |

- 段の時間と字幕の遅れは別の時計で測るため、段の合計と字幕の遅れは一致しません。差は、通訳ワーカーの待ち行列へ入るまでと、段の間の受け渡しの時間です。
- 字幕の遅れは、アプリサーバーの時計（壁時計）の 2 つの読み取りの差です。WSL2 のように壁時計が単調増加時計と違う進み方をする環境では、その分だけずれます（開発環境で毎分約 2 秒のずれを測った記録があります。[jobs.md](jobs.md) と、GitHub の PBI 5.3 のコメント）。
- `first_subtitle_ms` の起点は、会議を作った時点（`POST /api/meetings` が会議を保存した日時）です。利用者がブラウザーの共有の確認に答えている時間は、会議を作る前なので含みません。

### 会議の開始・終了・中断

| `process_type` | 出す時点 | 項目 |
|---|---|---|
| `meeting_started` | 会議を作った時点 | `meeting_id` |
| `meeting_ended` | 届いている音声を最後まで字幕にし、終了日時と状態を保存した時点 | `meeting_id`、`duration_ms`（会議の長さ）、`item_count`（字幕の件数） |
| `meeting_interrupted` | 中断にした時点（接続が切れた・通訳ワーカーを起動し直せなかった）。終了とは別の種類 | 同上 |

判定に使う会議の終了は、終了ボタンを受け付けた時点ではなく、`meeting_ended` を出した時点です。そのあとに字幕にした分が区間の外に出ないようにするためです。

### プロセスごとのメモリの使用量（`process_memory`）

会議の終了・中断の時点と、作成ジョブの終了の時点に、動いているプロセスごとに 1 行を出します。動いていないワーカーの行は出ません。

| 項目 | 意味 |
|---|---|
| `memory_trigger` | 時点。`meeting_ended`・`meeting_interrupted`・`job_finished` |
| `process_role` | `app_server`（アプリサーバー）・`interpreter_worker`（通訳ワーカー）・`generation_worker`（生成ワーカー）・`conversion_process`（変換プロセス）・`container`（コンテナ全体） |
| `memory_mb` | いまの常駐メモリ（`/proc/<番号>/status` の `VmRSS`）。1 MB は 1,048,576 バイト |
| `peak_memory_mb` | 常駐メモリの最大値（`VmHWM`）。取れなければ出ない |
| `job_type` | 作成ジョブの終了のときだけ付く（`summary` か `questions`） |

- 実装は `backend/src/meeting_interpreter/process_memory.py` です。標準ライブラリだけで `/proc` を読みます（新しいパッケージは入れていません）。通訳ワーカー・生成ワーカー・変換プロセスは、アプリサーバーの子のプロセスのうち、起動の引数が `-m <モジュール名>` で一致するものを見つけます。
- 会議の終了の値は、**届いている音声をワーカーへ渡し終え、終了処理を頼む直前**に取ります。通訳ワーカーは終了処理のあと自分で終わるため、会議を閉じる時点では、もう読めないからです。このため、通訳ワーカーの最終のメモリは、ワーカーが止まるときに自分で出す `interpreter_worker_stopped` の `peak_memory_mb` と食い違うことがあります（こちらは終了処理の間の増加も含みます）。
- 作成ジョブの終了の値は、`job_finished` を出した直後に取ります。会議中に作る質問では、通訳ワーカーも並びます。
- 終了の保存に失敗した会議を、あとで終了し直したとき（通訳ワーカーが無いため、セッションを経ずに終了する）は、メモリの記録を出しません。
- コンテナ全体は、cgroup の `memory.current`（v1 は `memory/memory.usage_in_bytes`）です。ファイルのキャッシュ（AI モデルのファイルなど）を含むため、プロセスの常駐メモリの合計より大きく出ます。取れない環境では出ません。
- 基本設計書の上限の仮置き（会議中 2.5GB、会議中に質問を作っている間 7.0GB など）と比べるときは、4 つのプロセスの常駐メモリの合計を使います。集計コマンドが「合計」の行を出します。

## 集計コマンド

`tools/summarize_processing_log.py`（`output_system/` で実行）は、コンテナのログから処理ログを読み、会議ごとの集計を Markdown の表で出します。標準ライブラリだけで動きます。

```bash
# コンテナのログをそのまま渡す（JSON でない行は読み飛ばす）
docker logs toshiakimamada-blip-mmd-output-system 2>&1 | python3 -I tools/summarize_processing_log.py

# ファイルから読む。会議番号で絞り込む（何回でも指定できる）
python3 -I tools/summarize_processing_log.py app.log --meeting <会議番号>

# 字幕の遅れの目標を変える（既定は 10 秒）
python3 -I tools/summarize_processing_log.py app.log --limit-seconds 8
```

出す表は 3 つです。

1. 会議ごとの字幕の遅れ: 開始（UTC）・終わり方（終了・中断・終わりの記録なし）・会議の長さ・字幕の件数・遅れの中央値・95 パーセンタイル・最大・10 秒を超えた件数・最初の字幕までの時間
2. 会議ごとの段の所要時間: 区切りの長さ・待ち・文字起こし・翻訳・保存と通知（それぞれ「中央値 / 最大」）
3. メモリの使用量: 時点ごと・プロセスごとの常駐メモリと最大値、4 つのプロセスの合計

数え方は、次のとおりです。

- 中央値は、小さい順の真ん中の値です。件数が偶数のときは、真ん中の 2 つの平均です。
- 95 パーセンタイルは、最近順位法です。小さい順に並べた「0.95 × 件数」を切り上げた番号の値（実際に出た値）です。
- 10 秒を超えた件数は、遅れが 10 秒より長い字幕の数です。ちょうど 10 秒は数えません。
- `docker logs -t` が付ける行頭の日時は読み飛ばします。終了コードは、会議の記録があれば 0、無ければ 1 です。

**このコマンドは、字幕の遅れの判定から除く区間の規則を適用しません。** 質問の作成中・ほかの会議の要約・AI モデルの読み込みの区間を切らずに、すべての字幕を数えます。作成ジョブの作成時間も集計しません。出力の先頭に、そのことを必ず書きます。目標に届いたかの判定には、この表の値を使いません。区間の規則の適用と作成時間の集計は、性能の測定を扱う後続の作業（Epic 8）で足します。

## 動作の確認

2026-11-18 19:00〜19:10 JST に、出荷するイメージを `docker compose build` で作り直し、コンテナを作り直したあと（`docker compose ps` が healthy、モデルは `ready`、本物のモデル）で、開発用コンテナからコンテナ名で接続して確かめました。音声は、[meetings.md](meetings.md) の確認と同じ英語の演説（faster-whisper の `tests/data/jfk.flac`。SHA-256 の先頭 `63a4b1e4`）を、1 秒の無音をはさんで繰り返し、実際の速さで送りました。リポジトリには入れていません。コンテナにイメージの新しいコードが入っていることは、`/app/src/meeting_interpreter/process_memory.py` の有無で確かめました。

| 会議 | 流し方 | 終わり方 |
|---|---|---|
| 1 回目 | 既存の測定道具 `backend/test/measure/measure_question_during_meeting.py`（音声 200 秒、開始の 50 秒後に質問を 1 回依頼） | 道具が接続を閉じて、中断になった |
| 2 回目 | 同じ道具の送信の部品で 60 秒送り、`POST /api/meetings/{会議番号}/end` で終了し、要約が `completed` になるまで待った（スクリプトは使い捨て） | 終了 |

`docker logs` の出力（182 行）を、集計コマンドへそのまま渡しました。

```bash
docker logs toshiakimamada-blip-mmd-output-system > app.log 2>&1
python3 -I tools/summarize_processing_log.py app.log
```

結果の要点は、次のとおりです（表の全体は、コマンドの出力にあります）。

| 会議 | 字幕の件数 | 遅れ 中央値 / 95 パーセンタイル / 最大（秒） | 10 秒を超えた件数 | 最初の字幕まで（秒） |
|---|---|---|---|---|
| 1 回目（中断） | 50 | 4.79 / 6.71 / 19.60 | 1 | 5.68 |
| 2 回目（終了） | 15 | 4.58 / 4.81 / 4.81 | 0 | 4.47 |

| 会議・時点 | アプリサーバー | 通訳ワーカー | 生成ワーカー | 4 プロセスの合計 | コンテナ全体 |
|---|---|---|---|---|---|
| 1 回目・質問の作成の終了（会議中） | 24.6 | 642.9 | 3433.3 | 4100.8 | 4887.6 |
| 1 回目・会議の中断 | 25.4 | 643.1 | 動いていない | 668.5 | 1465.5 |
| 2 回目・会議の終了 | 28.0 | 763.8 | 動いていない | 791.8 | 2253.3 |
| 2 回目・要約の作成の終了 | 27.8 | 動いていない | 3478.2 | 3506.0 | 5291.9 |

単位は MB です。この表の値は、この開発環境（4 コア、WSL2）の参考値です。区間の規則を適用していないため、目標に届いたかの判定には使えません。

確かめたこと（事実）

- 字幕の件数と遅れが、測定道具が通知から数えた値と一致しました。1 回目は、道具の側も字幕 50 件、10 秒を超えた字幕 1 件、最大 19.6 秒でした。
- 10 秒を超えた 1 件は、会議の最後の字幕です。区切りの長さ 2.78 秒、待ち 0.0019 秒、文字起こし 1.64 秒、翻訳 0.13 秒で、段の合計は約 4.6 秒です。残りの約 15 秒は、音声を送り終えてから接続を閉じるまでの時間にあたります。測定道具は、最後の発話のあとに無音を送りません。区切りが、接続を閉じるまで確定しなかったと考えられます（推測。無音を足した確認はしていません）。
- コンテナの中の `/proc` を直接読んだ値が、ログの値と合いました。アプリサーバー（番号 7）は、常駐 28,556 kB（27.9 MB）、最大 56,408 kB（55.1 MB）で、ログの `peak_memory_mb` 55.1 と同じです。
- 動いていないワーカーの行は出ませんでした（1 回目の中断と 2 回目の終了に生成ワーカー、2 回目の要約の終了に通訳ワーカー）。変換プロセスは、動いていないため出ません。
- ログ全体（182 行）に、タイトル（「測定」「測定B」）と、演説の語（country・Americans・ask not）は 1 件もありませんでした。処理ログで、捨てた項目の数 `dropped_field_count` を持つ行は 0 件、エラーログは 0 件でした。
- 集計コマンドは、JSON ではない行（4 行。ctranslate2 と ONNX Runtime の警告）と、処理ログではない JSON の行（runtime 75 行）を読み飛ばして、終了コード 0 で表を出しました。処理ログは 103 行です。

## 確かめていないこと

- 利用者の PC（Windows の Edge）の、実際の会議の音声での値。手順は [measure-early.md](measure-early.md) です。
- 2 時間の会議での、ログの量とメモリの推移。
- cgroup v1 の環境での、コンテナ全体の値（見本のファイルでだけ確かめました）。
- 通訳ワーカーの最終のメモリは、終了処理を頼む直前の値です。終了処理の間の増加は含みません。この確認では、ワーカーが止まるときに自分で出した `interpreter_worker_stopped` の `peak_memory_mb`（822.5 と 822.0）が、直前に取った最大値（822.5 と 822.0）と同じでした。会議の最後に大量の音声がたまっている場合は、値が違うことがあります（未確認）。
