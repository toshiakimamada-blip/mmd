# エラーの扱い

画面へ返すエラーの共通の形と、エラーコードの一覧です。分類と見せ方は、基本設計書の横断設計規約「エラーの分類と見せ方」と、画面設計書「エラー表示パターン」にあります。

## 共通の形

サーバーが画面へ返すエラーは、次の 4 項目だけを持つ JSON です。

```json
{
  "category": "business_error",
  "code": "MEETING_ALREADY_RUNNING",
  "message": "進行中の会議があります。",
  "action": "進行中の会議を終了してから、新しい会議を開始してください。"
}
```

| 項目 | 内容 |
|---|---|
| `category` | 分類。`input_error`（入力エラー）・`business_error`（業務エラー）・`system_error`（システムエラー） |
| `code` | エラーコード。`領域_出来事`（大文字・アンダースコア）。領域は `AUDIO`・`MEETING`・`SUBTITLE`・`SUMMARY`・`QUESTION`・`RECORD`・`MODEL`・`ACCESS`・`SYSTEM` の 9 つ |
| `message` | 何が起きたか。固定の文。会議の内容を入れない |
| `action` | 利用者が次に行う操作。固定の文。会議の内容を入れない |

プログラムの例外の文面とスタックトレースは、画面にもログにも出しません。

## サーバーでの起こし方

分類ごとの例外を起こします（`backend/src/meeting_interpreter/errors.py`）。

| 例外 | 分類 | HTTP の状態（既定） | ログ |
|---|---|---|---|
| `InputAppError` | 入力エラー | 422 | 出さない |
| `BusinessAppError` | 業務エラー | 409 | エラーログ・警告 |
| `SystemAppError` | システムエラー | 500 | エラーログ・異常 |

```python
raise BusinessAppError(
    "MEETING_ALREADY_RUNNING",
    "進行中の会議があります。",
    "進行中の会議を終了してから、新しい会議を開始してください。",
    meeting_id=meeting_id,
)
```

- コードの形が誤っていると、例外を作った時点で失敗します。
- `status_code` で HTTP の状態を変えられます（例: 存在しない会議は 404）。
- `component` を省くと、例外を起こしたモジュールの名前が入ります。

### WebSocket の処理で起こしたとき

WebSocket の処理（接続を受け付けたあとの処理）では、HTTP の応答を返せません。分類ごとの例外を起こすと、ログを出したあとに、接続を閉じます。

| 分類 | 閉じる符号 | 閉じる理由 | ログ |
|---|---|---|---|
| 入力エラー | 1008（方針に反する要求） | エラーコード | 出さない |
| 業務エラー | 1008（方針に反する要求） | エラーコード | エラーログ・警告 |
| システムエラー | 1011（サーバーの内部エラー） | エラーコード | エラーログ・異常 |

- 画面は、閉じる理由のエラーコードから、画面側の一覧の文言を引きます。閉じる理由を読んで表示に結びつける処理は、まだありません。接続を扱う機能の作業で足します。
- 閉じる理由には、分類の本文（`message` と `action`）を入れません。エラーコードだけを入れます。
- 接続を受け付ける前に起こすと、接続は 403 で断られます。符号と理由は相手に届きません。ログは同じです。
- 処理がすでに接続を閉じているとき、相手がすでに切れているときは、重ねて閉じません。想定外のエラーとしても記録しません。
- エラーコードが閉じる理由の上限（123 バイト）を超えるときは、理由を空にします。途中で切ると、別のコードに見えるためです。
- 想定外の例外は、次の節のとおり、1011 で閉じます。

### 想定外の例外

どの分類にも当てはまらない例外は、`UnhandledErrorMiddleware` が `SYSTEM_UNEXPECTED_ERROR`（HTTP 500）に変えます。

- 応答の本文に、例外の文面は入りません。
- エラーログ（異常）に、例外の種類（`exception_type`）と発生場所（`location`）だけを出します。
- 例外は外へ伝えません。外へ伝えると、サーバー（uvicorn）が文面つきのスタックトレースを記録します。
- WebSocket では、接続を内部エラーの符号（1011）で閉じます。
- 応答が始まったあとの例外は、本文を変えられないため、エラーログだけを出します。

FastAPI が自動で返す応答も、共通の形に変えています。

| 場面 | コード | 分類 |
|---|---|---|
| 要求の内容が決めた形でない（FastAPI の検証の失敗） | `SYSTEM_INVALID_REQUEST` | 入力エラー（422）。送られた値は返しません |
| 存在しない経路・存在しないファイル | `SYSTEM_ROUTE_NOT_FOUND` | システムエラー（404） |
| 経路で許していないメソッド | `SYSTEM_METHOD_NOT_ALLOWED` | システムエラー（405） |
| そのほかの HTTP の例外 | `SYSTEM_REQUEST_FAILED` | システムエラー（元の状態） |

## 画面での扱い

画面は、サーバーが返した `message` と `action` を表示しません。エラーコードごとの文言を、画面側の一覧から引きます（`frontend/src/errors/errorMessages.ts`）。

- 一覧に無いコードには、分類ごとの汎用の文言を出します。コードは必ず添えて表示します。
- 応答の本文が共通の形でないとき（プロキシの HTML のエラーなど）は、`SYSTEM_UNEXPECTED_ERROR` として扱います（`readErrorResponse`）。

## エラーコードを足す手順

1. サーバーで、分類に合う例外を起こします。コードは `領域_出来事` の形にします。
2. 画面の `ERROR_WORDINGS` に、同じコードの文言（何が起きたか・次に行う操作）を足します。
3. 文言は、業務用語辞書（データモデル設計書）の用語にそろえ、会議の内容を入れません。

## 登録済みのコード

| コード | 分類 | 何が起きたか |
|---|---|---|
| `SYSTEM_UNEXPECTED_ERROR` | システムエラー | 予期しない問題が起きました |
| `SYSTEM_ROUTE_NOT_FOUND` | システムエラー | 要求された経路がありません |
| `SYSTEM_INVALID_REQUEST` | 入力エラー | 送った内容に誤りがあります |
| `SYSTEM_METHOD_NOT_ALLOWED` | システムエラー | この操作は受け付けられません |
| `SYSTEM_REQUEST_FAILED` | システムエラー | 要求を処理できませんでした |
| `SYSTEM_CONFIG_INVALID` | システムエラー | 設定に誤りがあり、起動できません（起動の失敗のエラーログにだけ出ます。画面には出ません） |
| `ACCESS_HOST_NOT_ALLOWED` | 業務エラー | この宛先からは、アプリを利用できません（宛先 Host が `localhost`・`127.0.0.1`・コンテナ名のどれでもない） |
| `ACCESS_ORIGIN_MISSING` | 業務エラー | 送り元を確かめられない要求です（状態を変える要求で、送り元 Origin が付いていない） |
| `ACCESS_ORIGIN_MISMATCH` | 業務エラー | アプリの画面とは別の送り元からの要求です（送り元 Origin が、宛先と同じ接続先ではない） |

`ACCESS_*` の 3 つは、接続制限部（`access.py`）が要求を断るときに返します（HTTP の状態は 403）。例外を起こさず共通の形の本文を直接返すため、エラーログには出ません。断った記録は接続ログに出ます（README の「接続制限」を参照）。

### AI モデルの入手（MODEL_*）

入手に失敗した原因の種類ごとのコードです。準備状況の取得（`GET /api/models/status`）と通知の `error_code` に入ります。HTTP のエラーとしては返しません（準備状況の一部のため）。画面は、このコードから文言を引きます。

| コード | 分類 | 原因の種類（`failure_kind`） | 何が起きたか |
|---|---|---|---|
| `MODEL_NETWORK_UNREACHABLE` | システムエラー | `network_unreachable` | ネットワークにつながらない（名前が引けない、接続を断られた、経路が無い） |
| `MODEL_CERTIFICATE_INVALID` | システムエラー | `certificate_invalid` | 配布元の証明書を確かめられない（社内のネットワークの証明書が未登録の場合など） |
| `MODEL_SOURCE_UNRESPONSIVE` | システムエラー | `source_unresponsive` | 配布元が応答しない（時間切れ、エラーの応答、途中で切れた）。転送先が HTTPS でない、または許したホストでない場合も、ここに入れる |
| `MODEL_HASH_MISMATCH` | システムエラー | `hash_mismatch` | 入手したファイルが、定義の SHA-256（配布元のもの）と一致しない。そのファイルは捨てた |
| `MODEL_DISK_INSUFFICIENT` | システムエラー | `disk_insufficient` | ディスクの空きが足りない。入手を始める前の確認で足りないとき、書き込みで空きが無くなったとき。翻訳モデルの変換の前の確認と、変換の書き込みでも同じ |
| `MODEL_CONVERSION_FAILED` | システムエラー | `conversion_failed` | 翻訳モデルを、実行基盤の形式へ変換できない（変換プロセスの失敗、時間切れ）。変換の途中のファイルは捨てた。入手したファイルは残る |
| `MODEL_DOWNLOAD_FAILED` | システムエラー | `unknown` | 上のどれにも分類できない失敗（想定外）。例外の種類と発生場所がエラーログに出る |
| `MODEL_RETRY_NOT_ALLOWED` | 業務エラー（409） | — | 入手失敗でないときに、入手のやり直しを求めた（`POST /api/models/retry`） |

- 入手のやり直し（`POST /api/models/retry`）は、入手失敗のうち、変換の失敗にも使えます。入手済みのファイルは一致を確かめるだけで入手し直さず、変換だけをやり直します。

### 音声の取り込み（AUDIO_*）

ブラウザーで音声を取り込めなかったときの理由の種類です。サーバーは返しません。画面の取り込みの部品（`frontend/src/audio/audioErrors.ts` の `AudioCaptureError`）が、ブラウザーが返した例外の名前から決めます。例外の文面（共有していたウィンドウの名前などが混ざりうる）は、画面にもログにも出しません。使い方は `docs/audio-capture.md` です。

| コード | 何が起きたか |
|---|---|
| `AUDIO_NO_AUDIO_SHARED` | 画面共有に音声が含まれない（音声の共有をオンにしていない） |
| `AUDIO_PERMISSION_DENIED` | 共有の確認で取りやめた・拒否した、またはマイクの利用を拒否した。ブラウザーは、取りやめと拒否のどちらにも同じ例外（`NotAllowedError`）を返し、見分けがつかないため、1 つのコードにそろえる |
| `AUDIO_MIC_NOT_FOUND` | マイクが見つからない |
| `AUDIO_CAPTURE_FAILED` | 上のどれにも当てはまらない失敗（デバイスが使用中、安全な接続でないページ、変換の部品を読み込めない、など） |

### 会議中の取り込み停止（AUDIO_CAPTURE_STOPPED）

会議中に音声の共有が止まった・マイクが外れたときに、字幕の状況が取り込み停止になった時点で、画面が選択を求めるお知らせに出すコードです。サーバーは返しません。画面の `meetings/useCaptureStoppedChoice.ts` が決めます。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `AUDIO_CAPTURE_STOPPED` | システムエラー | 会議中に、音声の取り込みが止まった。それまでの字幕は残っている。利用者は、取り込みをやり直すか、会議を終了するかを選ぶ（[「会議中」の画面](live-screen.md)） |

- 音声を送る接続が閉じたあとに「取り込みをやり直す」を選んだときは、取り込みの失敗（`AUDIO_CAPTURE_FAILED`）にしません。会議の中断として、`MEETING_CONNECTION_LOST` を出します（下の「会議中の会議の中断」）。

### 会議中の会議の中断（MEETING_CONNECTION_LOST）

「会議中」の画面が、理由のエラーを受けずに会議の中断に気づいたときに、お知らせ帯に出すコードです。サーバーは返しません。画面の `meetings/useMeetingInterruption.ts` が決めます。画面は、お知らせを出したあと、その会議の「会議の記録」へ移ります（[「会議中」の画面](live-screen.md)の「会議の中断」）。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `MEETING_CONNECTION_LOST` | システムエラー | 会議が中断になったが、画面は理由のエラーを受けていない。中断の通知（`meeting.state_changed`）だけを受けた、つなぎ直したときに会議の記録を読むと中断だった、または、取り込みのやり直しで音声を送る接続が閉じていると分かった。それまでの字幕は保存されていて、会議の記録から要約を作れる |

- 文面は「会議が中断になりました。」で、原因を言い切りません。次に行う操作として、会議の記録で状態と字幕を確かめること、通訳を続けるときは新しい会議を開始することを案内します。画面は中断の原因を知らないためです。音声を送る接続が切れたときのほか、つなぎ直したときや、接続が閉じたあとのやり直しで気づいたときは、通訳ワーカーを起動し直せなかった中断のこともあります。
- 通訳ワーカーを起動し直せずに中断したことを画面が通知で受けたときは、アプリサーバーが通知する `SYSTEM_INTERPRETER_UNAVAILABLE`（下の「会議の開始と終了」）を出し、このコードは出しません。アプリサーバーは、そのエラーを、状態の変化より先に送ります。

### 記録のコピー（RECORD_COPY_FAILED）

「会議の記録」のコピーのボタンで、ブラウザーがクリップボードへの書き込みを断ったときのコードです。サーバーは返しません。画面のコピーの部品（`frontend/src/records/useClipboardCopy.ts`）が決めます。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `RECORD_COPY_FAILED` | システムエラー | クリップボードへ書き込めない。ブラウザーが書き込みを断った（`NotAllowedError`）。または、`navigator.clipboard` が無い（`localhost` と https 以外の接続で開いたページ） |

- お知らせ帯に、コピーできなかったことと、手でコピーする方法を出します。ボタンの下には、文面を入れた読み取り専用の欄を出します。欄の文面は選んであり、Ctrl+C でコピーできます。
- 例外の文面は、画面にもログにも出しません。会議の内容が混ざる余地を断つためです。
- 同じ操作が成功すると、お知らせと欄は消えます。

### 記録の取り出し（RECORD_EXPORT_FAILED）

「会議の記録」の「取り出す」で、ブラウザーがダウンロードを始められなかったときのコードです。サーバーは返しません。画面の取り出しの部品（`frontend/src/records/useRecordExport.ts`）が決めます。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `RECORD_EXPORT_FAILED` | システムエラー | ダウンロードを始められない。一時的な URL（`URL.createObjectURL`）を作れない、またはアンカーのクリックが例外を投げた |

- お知らせ帯に、取り出せなかったことと、もう一度「取り出す」を押す操作を出します。次に取り出せると、お知らせは消えます。
- 例外の文面は、画面にもログにも出しません。会議の内容（タイトルなど）が混ざる余地を断つためです。
- ブラウザーが、ダウンロードを始めたあとで断る場合（保存先の選択を取りやめた、複数ファイルの確認で拒否した、など）は、画面から見分けられません。このコードは出ません。

### 会議記録の保存（RECORD_*）

記録保存部（`backend/src/meeting_interpreter/records/store.py`）の書き込みの関数（会議の作成・字幕の追加・状態と終了日時の更新・記録の削除）が起こすエラーです。どれもシステムエラー（500）で、画面にはお知らせ帯または該当する欄に出します。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `RECORD_SAVE_FAILED` | システムエラー | データベースの操作が失敗した（ディスクがいっぱい・ほかの接続のロック・書き込みの失敗・破損など）。原因によらず、この 1 つのコードにそろえる。確定は取り消され、保存しようとした内容は何も残らない |
| `RECORD_VALUE_INVALID` | システムエラー | 保存しようとした値が、桁の上限・区分コード・日時の形・会議番号に合わない。画面や呼び出し側の確認をすり抜けた値の最後の防ぎ。何も保存しない。どの項目かは、例外の `field` が持つ（値は持たない） |
| `RECORD_DELETE_FAILED` | システムエラー | 会議の記録を削除できない。更新前の控えから消せない、または記録データベースの削除が失敗した（原因によらず、この 1 つのコードにそろえる）。記録データベースの行は 1 件も消えない。控えから先に消せていた場合も、控えから消した会議は戻さない。利用者は、削除をやり直せる |

- 保存しようとした内容（タイトル・字幕の本文など）は、例外にも、画面へ返す 4 項目にも含めません。データベースの例外は原因（`__cause__`）として持ち、文面はどこにも出しません。
- エラーログは、記録保存部が、失敗した関数の出口で 1 件出します（異常のレベル）。項目は、エラーコード・コンポーネント（`record_store`）・会議番号・例外の種類・発生場所だけです。呼び出し側がこの例外をそのまま上げても、例外の受け皿は重ねて出しません（`RecordError.log_level` が無し）。
- 字幕の保存に失敗したときの会議の続け方（その字幕を画面へ送らず、会議は続ける）は、呼び出し側が決めます。記録保存部は、失敗を伝えるところまでを受け持ちます。
- 読み出しの関数（`get_meeting`・`list_subtitles`）は、データベースの例外を変換しません。読み出しの失敗は、閲覧の機能が扱います。
- 記録データベースの構造が、このアプリの版では使えないときは、起動時に `RECORD_SCHEMA_UNSUPPORTED` をエラーログに出します（画面には出しません）。

各機能のコードは、その機能の作業で足します。

### 会議の開始と終了（MEETING_*・MODEL_NOT_READY・SYSTEM_INTERPRETER_UNAVAILABLE）

会議管理部（`backend/src/meeting_interpreter/meetings/`）が返すエラーです。文言に、タイトルなど会議の内容は入れません。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `MEETING_TITLE_INVALID` | 入力エラー（422） | タイトルが 100 文字を超える、または改行を含む（空白だけのタイトルは未入力として扱い、エラーにしない） |
| `MEETING_AUDIO_SOURCE_INVALID` | 入力エラー（422） | 音声の出どころが、`system_audio` でも `microphone` でもない |
| `MODEL_NOT_READY` | 業務エラー（409） | AI モデルが準備完了でないのに、会議を開始しようとした |
| `MEETING_ALREADY_RUNNING` | 業務エラー（409） | 通訳中の会議があるのに、新しい会議を開始しようとした |
| `MEETING_NOT_FOUND` | 業務エラー（404） | 会議番号に合う会議が無い（終了の要求、音声の接続） |
| `MEETING_NOT_RUNNING` | 業務エラー（409） | 通訳中でない会議へ、音声を送ろうとした（音声の接続は 403 で断られる） |
| `MEETING_AUDIO_ALREADY_CONNECTED` | 業務エラー（409） | この会議には、すでに音声の接続がある（2 本目の接続は 403 で断られる） |
| `MEETING_INVALID_TRANSITION` | 業務エラー（409） | 遷移規則の表に無い遷移を求められた |
| `MEETING_DELETE_NOT_ALLOWED` | 業務エラー（409） | 通訳中または要約作成中の会議を、削除しようとした（`DELETE /api/meetings/{会議番号}`）。何も削除しない |
| `MEETING_HAS_ACTIVE_JOB` | 業務エラー（409） | 要約か質問の作成ジョブが、待機中か作成中の会議を、削除しようとした。何も削除しない |
| `SYSTEM_INTERPRETER_UNAVAILABLE` | システムエラー（通知で届く） | 通訳ワーカーが止まり、起動し直せなかったため、会議を中断にした。`error.occurred` の通知で、会議の状態の変化（`meeting.state_changed`）より先に届く。「会議中」の画面は、お知らせ帯に出して「会議の記録」へ移る |

- 音声の WebSocket の接続を断る 3 つ（`MEETING_NOT_FOUND`・`MEETING_NOT_RUNNING`・`MEETING_AUDIO_ALREADY_CONNECTED`）は、接続を受け付ける前に起こすため、画面には HTTP の 403 として見えます。エラーコードは、サーバーのエラーログにだけ出ます。
- エラーの通知（`error.occurred`）は、`/ws/events` で届きます。項目は `meeting_id`・`category`・`code`・`message`・`action` です。画面は、`code` から画面側の文言を引きます。

### 字幕の処理（SUBTITLE_*）

会議中の字幕の処理が失敗したときの、会議管理部（`backend/src/meeting_interpreter/meetings/`）の通知です。HTTP の応答ではなく、`error.occurred` の通知で届きます。分類はシステムエラーです。会議は続けます。文言に、会議の内容とプログラムの例外の文面は入れません。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `SUBTITLE_TRANSCRIPTION_FAILED` | システムエラー（通知で届く） | 発話の区切り 1 つの文字起こしに失敗し、その区切りを飛ばした。同じ失敗が続いても、通知は調整値 `error_notice_interval_seconds` の間隔につき 1 件にまとめる |
| `SUBTITLE_SAVE_FAILED` | システムエラー（通知で届く） | 字幕 1 件の保存に失敗し、その字幕を画面へ送らなかった。原因（ディスクがいっぱい・ロック・値が決めた形に合わない）によらず、同じコードにする。失敗した字幕は順番を使わない。同じ失敗が続いても、通知は同じ間隔につき 1 件にまとめる |

- 画面は、「会議中」のお知らせ帯に、エラーとして出します（`frontend/src/meetings/useSubtitleErrorNotices.ts`）。次に行う操作は、文字起こしの失敗が「会議はそのまま続けられます。字幕が出ない状態が続くときは、会議を終了して、新しい会議を開始してください」、字幕の保存の失敗が「会議はそのまま続けられます。このお知らせが続けて出るときは、ディスクの空きを確かめてください。空きが少ないときは、ほかのファイルを消して空きを作ってください」です。保存の失敗は、原因（ディスクがいっぱい・ロック・字幕が上限を超える）によらず同じ文面のため、ディスクの空きだけを原因として決めつけません。
- 字幕の保存の失敗は、エラーログにも `SUBTITLE_SAVE_FAILED`（コンポーネント `meeting_manager`）を、失敗のたびに出します。項目は、会議番号・失敗した字幕の処理の識別子（`trace_id`。同じ識別子の `subtitle_sent` は出ない）・例外の種類（`RecordSaveError` か `RecordValueError`）・発生場所です。字幕の本文とデータベースの例外の文面は出しません。記録保存部は、データベースの失敗の種類と場所を、`RECORD_SAVE_FAILED` で別に出します。
- 翻訳の失敗は、エラーにしません。日本語訳が空の字幕として保存して通知します（エラーログ `SUBTITLE_TRANSLATION_FAILED` だけを残します）。
- コードを足すときは、`useSubtitleErrorNotices.ts` の `SUBTITLE_ERROR_CODES` にも足します。足し忘れは、フロントエンドのテストが検出します。

### 要約の作成の依頼（SUMMARY_NO_CONTENT）

`POST /api/meetings/{会議番号}/summary`（要約を作る・作り直す）が返すエラーです。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `SUMMARY_NO_CONTENT` | 業務エラー（409） | 字幕が 0 件の会議の要約を依頼した。要約は作らず、状態も変えない。画面は「内容がありません」と表示する |

- 会議が無いときは `MEETING_NOT_FOUND`（404）、状態が遷移規則の表に無いとき（通訳中の会議など）は `MEETING_INVALID_TRANSITION`（409）です。
- 同じ会議の要約が待機中か作成中のときは、エラーにせず、そのジョブを返します（重複を防ぐ規約）。

### 質問の作成の依頼（QUESTION_NO_CONTENT）

`POST /api/meetings/{会議番号}/question-sets`（質問を作る）が返すエラーです。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `QUESTION_NO_CONTENT` | 業務エラー（409） | 字幕が 0 件の会議の質問を依頼した（空白だけの字幕しか無い場合を含む）。質問は作らず、会議の状態も変えない |

- 会議が無いときは `MEETING_NOT_FOUND`（404）です。質問は、会議の状態を問わず受け付けるため、`MEETING_INVALID_TRANSITION` は返しません。
- 同じ会議の質問が待機中か作成中のときは、エラーにせず、そのジョブを返します（重複を防ぐ規約）。

### 起動時の復旧（SUMMARY_INTERRUPTED・MEETING_RECOVERY_FAILED）

アプリが止まったとき、要約作成中だった会議は、起動時の復旧（`backend/src/meeting_interpreter/meetings/recovery.py`）が要約失敗にします。そのときの失敗理由として保存するコードです。HTTP の応答でも `error.occurred` の通知でもなく、会議の記録の `summary_failure_reason` に入って届きます。

| コード | 分類 | 何が起きたか |
|---|---|---|
| `SUMMARY_INTERRUPTED` | システムエラー | 要約を作っている間にアプリが止まった。作成ジョブは保存していないため、自動では作り直さない |

- 画面は、ほかの要約の失敗と同じく、会議の記録の要約の領域に、コードから引いた文言と「要約を作るボタン」の案内を出します。前の要約があれば、あわせて表示します。
- 通訳中だった会議は、エラーコードを使わず、中断にして終了日時を記録します。

起動時の復旧が失敗したときは、エラーログ `MEETING_RECOVERY_FAILED` を出します。画面には出ません（起動の途中の出来事で、画面はまだつながっていません）。

| コード | 分類 | 何が起きたか | ログの項目 |
|---|---|---|---|
| `MEETING_RECOVERY_FAILED` | システムエラー | 会議 1 件を直せなかった。字幕を読めなかった（データベースの例外、壊れた日時の値）。その会議は状態が変わらず、残りの会議は直して起動する。次の起動で、もう一度直す | コンポーネント `meeting_manager`、会議番号、例外の種類、発生場所 |
| `MEETING_RECOVERY_FAILED` | システムエラー | 会議の一覧を読めず、起動が止まった | コンポーネント `startup`、例外の種類、発生場所（会議番号なし） |

- どちらも、例外の文面は出しません。保存に失敗した会議（`RECORD_SAVE_FAILED`）は、記録保存部が会議番号つきで出すため、`MEETING_RECOVERY_FAILED` は重ねて出しません。
- 直せなかった会議の数は、処理ログ `startup_recovery` の `unrecovered_count` に出ます。

### 要約と質問の作成（SUMMARY_*・QUESTION_*）

作成ジョブ管理部（`backend/src/meeting_interpreter/jobs/`）が、要約と質問の作成に失敗したときに返すエラーです。HTTP の応答ではなく、`error.occurred` の通知で届きます。分類はすべてシステムエラーです。文言に、会議の内容は入れません。コードは `jobs/errors.py` の `error_code` が作ります（領域は、要約が `SUMMARY`、質問が `QUESTION`）。

| 出来事 | 何が起きたか |
|---|---|
| `*_GENERATION_FAILED` | 結果を作れなかった。作り直しても決めた形がそろわない（質問は、5 組に満たない・1 問が 500 文字を超える場合を含む）、または文章生成に失敗した。生成ワーカーは続ける |
| `*_WORKER_STOPPED` | 作成の途中で、生成ワーカーが止まった（強制終了やメモリ不足を含む）。待機中のジョブは、新しい生成ワーカーで続く |
| `*_WORKER_START_FAILED` | 生成ワーカーを起動できなかった（AI モデルを読み込めない、準備完了の時間切れなど） |
| `*_SAVE_FAILED` | 結果は作れたが、結果の受け取り先（保存）が失敗した |

- 失敗した作成ジョブが要約のときは、結果の受け取り先の `summary_failed(会議番号, エラーコード)` が呼ばれ、会議の状態が `summary_failed` になり、エラーコードが失敗理由として保存されます（画面を開き直しても表示できます）。作り直しに失敗したときは、前の要約が残ります。質問の失敗では、会議の状態を変えません。
- 生成ワーカーを起動する前に失敗したとき（会議の終了のあと、字幕を読み出せない、など）も、`SUMMARY_GENERATION_FAILED` を保存して、`error.occurred` で通知します。
- 画面は、コードから画面側の文言を引きます（`frontend/src/errors/errorMessages.ts`）。次に行う操作は、要約が「会議の記録で、要約を作るボタンを押す」、質問が「もう一度、質問を作るボタンを押す」です。
- エラーログには、コード・コンポーネント（`job_manager`）・会議番号・処理の識別子を出します。ワーカーが止まったときは、止まり方（`killed_by_signal_9` など）を `SYSTEM_GENERATION_WORKER_EXITED` の `exception_type` に出します。例外を捕まえて続ける箇所（結果の保存の失敗・起動の失敗・通知の失敗・管理のタスクの想定外の失敗）は、例外の種類（`exception_type`）と発生場所（`location`）を出します。例外の文面は出しません。
