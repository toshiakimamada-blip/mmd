# エラーの扱い

画面へ返すエラーの共通の形と、エラーコードの一覧です。分類と見せ方は、基本設計書の横断設計規約「エラーの分類と見せ方」と、画面設計書「エラー表示パターン」にあります。

## 共通の形

サーバーが画面へ返すエラーは、次の 4 項目だけを持つ JSON です。

```json
{
  "category": "business_error",
  "code": "MEETING_ALREADY_RUNNING",
  "message": "進行中の会議があります。",
  "action": "進行中の会議を終了してから、新しい会議を開始してください。"
}
```

| 項目 | 内容 |
|---|---|
| `category` | 分類。`input_error`（入力エラー）・`business_error`（業務エラー）・`system_error`（システムエラー） |
| `code` | エラーコード。`領域_出来事`（大文字・アンダースコア）。領域は `AUDIO`・`MEETING`・`SUBTITLE`・`SUMMARY`・`QUESTION`・`RECORD`・`MODEL`・`ACCESS`・`SYSTEM` の 9 つ |
| `message` | 何が起きたか。固定の文。会議の内容を入れない |
| `action` | 利用者が次に行う操作。固定の文。会議の内容を入れない |

プログラムの例外の文面とスタックトレースは、画面にもログにも出しません。

## サーバーでの起こし方

分類ごとの例外を起こします（`backend/src/meeting_interpreter/errors.py`）。

| 例外 | 分類 | HTTP の状態（既定） | ログ |
|---|---|---|---|
| `InputAppError` | 入力エラー | 422 | 出さない |
| `BusinessAppError` | 業務エラー | 409 | エラーログ・警告 |
| `SystemAppError` | システムエラー | 500 | エラーログ・異常 |

```python
raise BusinessAppError(
    "MEETING_ALREADY_RUNNING",
    "進行中の会議があります。",
    "進行中の会議を終了してから、新しい会議を開始してください。",
    meeting_id=meeting_id,
)
```

- コードの形が誤っていると、例外を作った時点で失敗します。
- `status_code` で HTTP の状態を変えられます（例: 存在しない会議は 404）。
- `component` を省くと、例外を起こしたモジュールの名前が入ります。

### WebSocket の処理で起こしたとき

WebSocket の処理（接続を受け付けたあとの処理）では、HTTP の応答を返せません。分類ごとの例外を起こすと、ログを出したあとに、接続を閉じます。

| 分類 | 閉じる符号 | 閉じる理由 | ログ |
|---|---|---|---|
| 入力エラー | 1008（方針に反する要求） | エラーコード | 出さない |
| 業務エラー | 1008（方針に反する要求） | エラーコード | エラーログ・警告 |
| システムエラー | 1011（サーバーの内部エラー） | エラーコード | エラーログ・異常 |

- 画面は、閉じる理由のエラーコードから、画面側の一覧の文言を引きます。閉じる理由を読んで表示に結びつける処理は、まだありません。接続を扱う機能の作業で足します。
- 閉じる理由には、分類の本文（`message` と `action`）を入れません。エラーコードだけを入れます。
- 接続を受け付ける前に起こすと、接続は 403 で断られます。符号と理由は相手に届きません。ログは同じです。
- 処理がすでに接続を閉じているとき、相手がすでに切れているときは、重ねて閉じません。想定外のエラーとしても記録しません。
- エラーコードが閉じる理由の上限（123 バイト）を超えるときは、理由を空にします。途中で切ると、別のコードに見えるためです。
- 想定外の例外は、次の節のとおり、1011 で閉じます。

### 想定外の例外

どの分類にも当てはまらない例外は、`UnhandledErrorMiddleware` が `SYSTEM_UNEXPECTED_ERROR`（HTTP 500）に変えます。

- 応答の本文に、例外の文面は入りません。
- エラーログ（異常）に、例外の種類（`exception_type`）と発生場所（`location`）だけを出します。
- 例外は外へ伝えません。外へ伝えると、サーバー（uvicorn）が文面つきのスタックトレースを記録します。
- WebSocket では、接続を内部エラーの符号（1011）で閉じます。
- 応答が始まったあとの例外は、本文を変えられないため、エラーログだけを出します。

FastAPI が自動で返す応答も、共通の形に変えています。

| 場面 | コード | 分類 |
|---|---|---|
| 要求の内容が決めた形でない（FastAPI の検証の失敗） | `SYSTEM_INVALID_REQUEST` | 入力エラー（422）。送られた値は返しません |
| 存在しない経路・存在しないファイル | `SYSTEM_ROUTE_NOT_FOUND` | システムエラー（404） |
| 経路で許していないメソッド | `SYSTEM_METHOD_NOT_ALLOWED` | システムエラー（405） |
| そのほかの HTTP の例外 | `SYSTEM_REQUEST_FAILED` | システムエラー（元の状態） |

## 画面での扱い

画面は、サーバーが返した `message` と `action` を表示しません。エラーコードごとの文言を、画面側の一覧から引きます（`frontend/src/errors/errorMessages.ts`）。

- 一覧に無いコードには、分類ごとの汎用の文言を出します。コードは必ず添えて表示します。
- 応答の本文が共通の形でないとき（プロキシの HTML のエラーなど）は、`SYSTEM_UNEXPECTED_ERROR` として扱います（`readErrorResponse`）。

## エラーコードを足す手順

1. サーバーで、分類に合う例外を起こします。コードは `領域_出来事` の形にします。
2. 画面の `ERROR_WORDINGS` に、同じコードの文言（何が起きたか・次に行う操作）を足します。
3. 文言は、業務用語辞書（データモデル設計書）の用語にそろえ、会議の内容を入れません。

## 登録済みのコード

| コード | 分類 | 何が起きたか |
|---|---|---|
| `SYSTEM_UNEXPECTED_ERROR` | システムエラー | 予期しない問題が起きました |
| `SYSTEM_ROUTE_NOT_FOUND` | システムエラー | 要求された経路がありません |
| `SYSTEM_INVALID_REQUEST` | 入力エラー | 送った内容に誤りがあります |
| `SYSTEM_METHOD_NOT_ALLOWED` | システムエラー | この操作は受け付けられません |
| `SYSTEM_REQUEST_FAILED` | システムエラー | 要求を処理できませんでした |
| `SYSTEM_CONFIG_INVALID` | システムエラー | 設定に誤りがあり、起動できません（起動の失敗のエラーログにだけ出ます。画面には出ません） |
| `ACCESS_HOST_NOT_ALLOWED` | 業務エラー | この宛先からは、アプリを利用できません（宛先 Host が `localhost`・`127.0.0.1`・コンテナ名のどれでもない） |
| `ACCESS_ORIGIN_MISSING` | 業務エラー | 送り元を確かめられない要求です（状態を変える要求で、送り元 Origin が付いていない） |
| `ACCESS_ORIGIN_MISMATCH` | 業務エラー | アプリの画面とは別の送り元からの要求です（送り元 Origin が、宛先と同じ接続先ではない） |

`ACCESS_*` の 3 つは、接続制限部（`access.py`）が要求を断るときに返します（HTTP の状態は 403）。例外を起こさず共通の形の本文を直接返すため、エラーログには出ません。断った記録は接続ログに出ます（README の「接続制限」を参照）。

### AI モデルの入手（MODEL_*）

入手に失敗した原因の種類ごとのコードです。準備状況の取得（`GET /api/models/status`）と通知の `error_code` に入ります。HTTP のエラーとしては返しません（準備状況の一部のため）。画面は、このコードから文言を引きます。

| コード | 分類 | 原因の種類（`failure_kind`） | 何が起きたか |
|---|---|---|---|
| `MODEL_NETWORK_UNREACHABLE` | システムエラー | `network_unreachable` | ネットワークにつながらない（名前が引けない、接続を断られた、経路が無い） |
| `MODEL_CERTIFICATE_INVALID` | システムエラー | `certificate_invalid` | 配布元の証明書を確かめられない（社内のネットワークの証明書が未登録の場合など） |
| `MODEL_SOURCE_UNRESPONSIVE` | システムエラー | `source_unresponsive` | 配布元が応答しない（時間切れ、エラーの応答、途中で切れた）。転送先が HTTPS でない、または許したホストでない場合も、ここに入れる |
| `MODEL_HASH_MISMATCH` | システムエラー | `hash_mismatch` | 入手したファイルが、定義の SHA-256（配布元のもの）と一致しない。そのファイルは捨てた |
| `MODEL_DISK_INSUFFICIENT` | システムエラー | `disk_insufficient` | ディスクの空きが足りない。入手を始める前の確認で足りないとき、書き込みで空きが無くなったとき。翻訳モデルの変換の前の確認と、変換の書き込みでも同じ |
| `MODEL_CONVERSION_FAILED` | システムエラー | `conversion_failed` | 翻訳モデルを、実行基盤の形式へ変換できない（変換プロセスの失敗、時間切れ）。変換の途中のファイルは捨てた。入手したファイルは残る |
| `MODEL_DOWNLOAD_FAILED` | システムエラー | `unknown` | 上のどれにも分類できない失敗（想定外）。例外の種類と発生場所がエラーログに出る |
| `MODEL_RETRY_NOT_ALLOWED` | 業務エラー（409） | — | 入手失敗でないときに、入手のやり直しを求めた（`POST /api/models/retry`） |

- 入手のやり直し（`POST /api/models/retry`）は、入手失敗のうち、変換の失敗にも使えます。入手済みのファイルは一致を確かめるだけで入手し直さず、変換だけをやり直します。

各機能のコードは、その機能の作業で足します。
