# 会議の開始と終了、字幕の保存と通知

会議管理部（`backend/src/meeting_interpreter/meetings/`）と通知部（`backend/src/meeting_interpreter/notify/`）の使い方と、動きの決めです。設計の根拠は、基本設計書の機能設計書 F-03・F-05・F-06・F-09、横断設計規約「会議の状態の遷移規則」「保存の単位と順序」「重複を防ぐ規約」、ADR-02・ADR-07・ADR-09 にあります。

## 画面から呼ぶ経路

| 経路 | 役割 |
|---|---|
| `POST /api/meetings` | 会議を開始する（201）。本文は `{"title": "…", "audio_source": "system_audio" または "microphone"}`。`title` は省略、空、空白だけでもよい（開始日時から作った文字列になる） |
| `POST /api/meetings/{会議番号}/end` | 会議を終了する（200）。本文は無し |
| `WebSocket /ws/audio/{会議番号}` | 画面からアプリサーバーへ、音声を送る。会議ごとに 1 本まで |
| `WebSocket /ws/events` | アプリサーバーから画面へ、通知（JSON）を送る。複数の画面が接続できる |

会議を返す応答の形は次のとおりです。日時は UTC のミリ秒までの文字列（`2026-11-05T01:23:45.678Z`）です。

```json
{
  "meeting_id": "8f0e…（32 桁の 16 進数）",
  "title": "週次の定例",
  "started_at": "2026-11-05T01:23:45.678Z",
  "ended_at": null,
  "audio_source": "system_audio",
  "status": "interpreting"
}
```

### 会議の開始

1. 入力を確かめます。タイトルは 100 文字以内で改行を含まず（前後の空白は取り除きます。空白だけは未入力）、音声の出どころは 2 つのどちらかです。誤りは入力エラー（422）です。
2. AI モデルが準備完了でなければ `MODEL_NOT_READY`、進行中の会議があれば `MEETING_ALREADY_RUNNING`（どちらも業務エラー、409）です。
3. 会議を作り（状態は通訳中）、会議番号を返します。通訳ワーカーの起動（AI モデルの読み込み）は待ちません。起動の間に届いた音声は、アプリサーバーがためておき、準備ができたあとに、届いた順に渡します。

画面は、音声を取り込めたあとで、この経路を呼びます（ADR-09: 準備中の会議は保存しません）。返った会議番号で、音声の WebSocket をつなぎます。

進行中の会議の判定は、アプリサーバーのメモリ（会議のセッション）で行います。アプリが止まったあとに通訳中のまま残った会議（起動時の復旧が直します。暫定版では未実装）を、進行中と数えないためです。

### 会議の終了

1. 音声の受け付けを止めます。
2. ためてある音声を通訳ワーカーへ渡し切り、終了処理を頼み、届いている音声を最後まで字幕にします。字幕は 1 件ずつ、受け取った順に保存して通知します。
3. 最後の字幕を保存したあとで、終了日時と状態を 1 回の確定で保存します。字幕が 1 件以上なら要約作成中、0 件なら完了です。
4. 通訳ワーカーを止めます。止めてから、要約を始める呼び出し（`on_meeting_ended`）を行います。作成ジョブ管理部ができるまでは、何もしません。そのため、字幕が 1 件以上の会議は、要約作成中のまま残ります。

終了の要求が 2 回届いたときは、2 回目は何も変えず、現在の状態を返します（処理の途中なら、1 回目の結果を待って同じ結果を返します）。通訳中でない会議への要求も同じです。

終了日時と状態を保存できなかったときは、状態を変えず（通訳中のまま）、`RECORD_SAVE_FAILED` を返します。通訳ワーカーは止めます。もう一度終了を求めると、字幕の件数から状態を決めて保存し直します。

### 画面との接続が切れたとき

音声の WebSocket が切れたら（ブラウザーを閉じた、再読み込みした、ネットワークが切れた）、届いている音声を字幕にしてから、状態を中断にします。終了日時は、接続が切れた日時です（字幕にし終えた日時ではありません）。終了の要求が先に来ていたときは、状態を変えません。字幕が 0 件でも、完了ではなく中断です。中断した会議の通訳は再開しません。

処理ログは、終了を `meeting_ended`、中断を `meeting_interrupted` で出します（会議番号・かかった時間・字幕の件数つき）。

開始のあと、音声の WebSocket が 1 本も張られない場合も、接続が切れたときと同じ手順で中断にします。待ち時間は、会議を開始してから `audio_connect_timeout_seconds`（30 秒）です。タブを閉じた、接続に失敗した、などで音声がつながらない会議が、通訳ワーカーを載せたまま残り、新しい開始を断り続けることを防ぎます。終了日時は、待ち時間が過ぎた日時です。このときは、処理ログに `audio_connect_timeout` も出ます。待ち時間のうちに音声が張られた会議は、この見張りの対象から外れます。

### 通訳ワーカーが止まったとき

異常終了を検出したら、通訳ワーカーを起動し直して、会議を続けます。起動の間に届いた音声は、捨てずにためて、起動し直したワーカーへ順に渡します（ワーカーが受け取っていた分は失われます）。起動の失敗または異常終了が続けて 3 回に達したら、起動し直しをやめて、会議を中断にし、エラー `SYSTEM_INTERPRETER_UNAVAILABLE` を通知します。回数と待ち時間は `config/tuning.toml` の調整値です（`interpreter_max_failures`・`interpreter_restart_wait_seconds`・`interpreter_stable_seconds`）。

- 壊れた出力を書いて動き続けるワーカー（`WorkerExited(protocol_error=True)`）は、受け取った時点で子を止めます。
- 停止完了に入っている「外へ通信を試みた回数」が 0 でなければ、エラーログ `SYSTEM_INTERPRETER_NETWORK_ATTEMPT` を出します（会議は続けます）。

### 固まったワーカー

通訳ワーカーが標準入力を読まなくなっても、会議の終了と中断は時間内に戻ります。

| 場面 | 区切り | 超えたとき |
|---|---|---|
| ためてある音声を渡し切る | `meeting_end_flush_timeout_seconds`（15 秒） | ワーカーを強制終了して、手元の字幕だけで閉じる |
| 終了処理の依頼を書き始める | 2 秒（`FINISH_WRITE_TIMEOUT_SECONDS`） | 同上 |
| 終了処理のあと、字幕が届かない | `meeting_end_finish_idle_seconds`（30 秒。字幕が届くたびに数え直す） | 同上 |
| ワーカーを止める | 2 秒と、強制終了の猶予 1 秒（`STOP_TIMEOUT_SECONDS`） | プロセスのグループごと強制終了 |

強制終了したときは、エラーログ `SYSTEM_INTERPRETER_NOT_RESPONDING` を出します。残りの音声は字幕になりません。

## 音声の WebSocket

- バイナリ: 16kHz・モノラル・16 ビット（リトルエンディアン）の PCM。画面は約 100 ミリ秒（3,200 バイト）ごとに送ります。1 件の上限は 64KB で、超えると 1008 で閉じます。
- テキスト: 制御の知らせ（JSON）`{"type": "capture.stopped"}`・`{"type": "capture.resumed"}`。受け取ると、`MeetingManager.subscribe_capture_events` で足した受け取り先へ渡します（字幕の状況の更新に使います。後続の作業）。JSON でない、`type` が無いものは、1008 で閉じます。知らない種類は読み捨てます。
- 届いた音声に、アプリサーバーの時計で届いた日時を付け、順番どおりに通訳ワーカーへ渡します。音声は保存しません。ワーカーへ渡したら、メモリから外します。ログに音声を書きません。
- 会議が無い、通訳中でない、すでに音声の接続がある場合は、接続を受け付けず、HTTP の 403 で断ります。
- 接続が切れたら、会議を中断にします（上記）。会議の終了や中断が済むと、サーバー側から 1000 で閉じます。

## 通知（`/ws/events`）

`{"type": "対象.出来事", …}` の形の JSON です。項目名は小文字のアンダースコア区切りです。

| 通知 | 項目 | 送る時点 |
|---|---|---|
| `subtitle.created` | `meeting_id`・`sequence`（字幕の順番）・`original_text`（英語の原文）・`translated_text`（日本語訳。訳せなかったときは `null`）・`spoken_at`（話された時刻） | 字幕の保存が確定したあと |
| `meeting.state_changed` | `meeting_id`・`status`・`ended_at`（通訳中は `null`） | 会議の開始、終了、中断 |
| `error.occurred` | `meeting_id`・`category`・`code`・`message`・`action` | 字幕の保存の失敗、終了の保存の失敗、通訳ワーカーの起動し直しの失敗 |
| `model.status_changed` | 準備状況の取得（`GET /api/models/status`）と同じ項目 | AI モデルの準備状況が変わったとき |

- 字幕は、保存が確定してから送ります。保存に失敗した字幕は送りません（`error.occurred` を送り、会議は続けます）。失敗した字幕は順番を使いません。
- 同じ順番の `subtitle.created` を 2 回送りません。画面は、同じ順番を 1 回だけ表示します。
- 日本語訳が無い字幕も、保存して送ります。
- 画面ごとに、送り待ちの通知を 1,000 件まで持ちます。読まずに超えた画面だけ、1013 で閉じます（ほかの画面と送る側は止まりません）。画面は、つなぎ直して、HTTP の取得で状況を読み直します。
- この WebSocket は一方向です。画面から届いた内容は読み捨てます。

## 会議の状態の遷移規則

遷移規則の表は、`meetings/transitions.py` の `TRANSITIONS` の 1 か所に持ちます（横断設計規約の表と同じ 15 行）。状態を変える前に `resolve_transition` で確かめ、表に無い遷移は業務エラー `MEETING_INVALID_TRANSITION` にします。状態を変えられるのは、会議管理部（`meetings/`）と、作る予定の作成ジョブ管理部（`jobs/`）だけです。`backend/test/meeting_interpreter/meetings/test_state_change_boundary.py` が、`update_meeting` を呼ぶ場所をこの 2 つに限ります。

## 通訳ワーカーの起動の入口

会議管理部は、通訳ワーカーのクライアントと開始のメッセージを、`InterpreterLauncher`（`meetings/workers.py`）から受け取ります。本番は `ProductionLauncher`（本物の AI モデル）です。自動テストは、偽のエンジンで動かす入口を `create_app(..., interpreter_launcher=…)` で渡します。アプリにテスト専用の分岐はありません（ADR-13）。

## 実機での確認（出荷するコンテナ、本物のモデル）

`docker compose build` と `docker compose up -d` で作ったコンテナ（準備状況が `ready`）の中で、`python` のスクリプトから、アプリへ `127.0.0.1:3001` でつないで確かめました。スクリプトはリポジトリに入れていません。音声は、faster-whisper の `tests/data/jfk.flac`（11.0 秒の英語の演説。SHA-256 の先頭 `63a4b1e4`）の前に 1 秒、後ろに 2 秒の無音を足し、実際の速さ（100 ミリ秒のフレームを 100 ミリ秒ごと）で送りました。

| 場面 | 確かめたこと | 結果 |
|---|---|---|
| 開始 | `POST /api/meetings` の応答 | 201、0.01 秒。通訳ワーカーの起動を待たない。ワーカーは別のプロセスで動き、会議の 6 秒後の常駐メモリは 777MB |
| 字幕 | 最初のフレームを送ってから、字幕の通知が届くまで | 3 件。5.5 秒・10.7 秒・13.9 秒。英語の原文と日本語訳つき（例: `And so, my fellow Americans...` → `従って、私の仲間のアメリカ人は...`） |
| 終了 | 声の途中までしか送らずに終了 | 1 回目の確認では、終了の時点で字幕は 2 件で、3 件目（`Ask what you can do for your country.`）が終了の処理の中で字幕になり、通知された。終了は 0.79 秒で戻り、状態は要約作成中 |
| 後始末 | 終了のあとのプロセス | 通訳ワーカーのプロセスは 0。終了を 2 回目に求めると、同じ終了日時で要約作成中のまま。終了した会議への音声の接続は 403 で断られた |
| 異常終了 | ワーカーを `kill -9` | 約 1 秒後に別のプロセスで起動し直され、続けて送った音声から字幕ができた |
| 接続切れ | 音声の接続を閉じる | 状態が中断になり、ワーカーのプロセスは 0。中断した会議への終了の要求は、中断のまま返った |
| ログ | コンテナの標準出力 | 字幕の本文とタイトルは出ていない。`SYSTEM_INTERPRETER_NETWORK_ATTEMPT`（外へ通信を試みた回数が 0 でない）は出ていない |

出荷するイメージを `docker compose build` で作り直し、コンテナを作り直したあとにも、同じ音声で確かめ直しました（開発用コンテナからコンテナ名で接続。27 項目すべて合格）。上の表に加えて、次のことを確かめています。

- 開始中に 2 回目の開始を求めると、`MEETING_ALREADY_RUNNING`（409）で断られる。
- 保存した字幕と通知した字幕が、件数・順番・原文・日本語訳まで一致する。順番は 1 から欠けずに並び、重ならない。
- 通訳ワーカーのプロセスに、ソケットが 1 つも無い。会議の間、コンテナの TCP 接続の相手は、接続している開発用コンテナだけだった（`/proc/net/tcp` の抜き取り。パケットの採取ではない）。
- コンテナの標準出力に、字幕の本文（英語・日本語）と会議のタイトルが出ていない。
- コンテナを作り直した直後の最初の会議は、モデルの読み込みで、最初の字幕の通知まで 36.7 秒かかった（ファイルのキャッシュが冷えていた）。同じコンテナの次の会議は 6.2 秒だった。

確かめていないことは次のとおりです。

- 画面（ブラウザー）からの操作。この作業は、アプリサーバーの側だけです。
- 利用者の PC（Windows の Edge）での、実際の PC の音声を使った動作。
- 長い会議（2 時間）での、メモリと字幕の遅れ。字幕の遅れの目標（10 秒以内）は、このコンテナでは 11 秒の音声 1 本でしか測っていません。測定は [docs/interpreter.md](interpreter.md) にあります。
- 複数の話者、専門用語、会議アプリ経由の音質。
- ONNX Runtime の Linux 版（1.31.0）は、利用状況を送る部品（送り先 `mobile.events.data.microsoft.com`）を内蔵しています。通訳ワーカーは OS の仕組み（seccomp）でソケットを作れないため、送れません。収集を止める呼び出し（`disable_telemetry_events`）も入れましたが、起動のたびに標準出力へ警告が 1 行出ます（`Failed to persist telemetry device ID; using an in-memory identifier`）。この行は JSON のログではありません。
